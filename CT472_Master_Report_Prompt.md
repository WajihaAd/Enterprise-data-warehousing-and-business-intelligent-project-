## Writing and evidence rules
For every meaningful implementation step explain WHAT was done, WHY, HOW (real logic/code), INPUT and OUTPUT, VALIDATION, and WHAT the result means. Tell the story in chronological order and use clear chapter transitions. Do not report repeated runtime resets, installing dependencies repeatedly, reconnections, routine retries or intermediate coding errors as accomplishments. Include substantive engineering decisions and controlled failure/recovery tests because they demonstrate system behavior. Avoid verbose chat-style repetition. Use accessible English but retain technical precision. Include numbered figures, tables, cross references and readable code; use original screenshots/ERDs with captions, not fabricated outputs. Redact credentials and personal source data. If a claim is unsupported mark it as not verified, and reconcile inconsistent counts transparently using latest valid evidence and scope.

Deliver one professional report, preferably editable DOCX and PDF if your environment supports both, with a real table of contents, consistent heading hierarchy, page numbers, clear tables and diagrams. Do not impose an arbitrary short page limit; depth should follow the evidence. Prepare an internal coverage checklist against every mandatory section before finalizing, and flag missing assignment evidence or actual dashboard screenshots instead of inventing them. Do not ask routine questions if reasonable placeholders suffice.
